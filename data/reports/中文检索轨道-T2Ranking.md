# 纯中文检索轨道（T2Ranking）

> 目标：做**原生中文、面向国内业务**的检索，并且用**真实人工相关性标注**评估（替掉英文那套
> 「答案字符串匹配」的代理指标）。日期：2026-09-26

---

## 1. 为什么选 T2Ranking（实测，不是猜）

| 候选 | 实测结果 | 判断 |
|---|---|---|
| **`THUIR/T2Ranking`** | ✅ 可下载，**含 collection + queries + qrels + 官方 BM25/DPR 基线 run** | **选它** |
| `PaddlePaddle/dureader-retrieval-ranking` | ❌ HTTP 401 | 拿不到 |
| `Alibaba-NLP/Multi-CPR` | ❌ HTTP 401 | 拿不到 |
| `mteb/t2ranking` / `mteb/cmteb` | ❌ HTTP 401 | 拿不到 |
| `miracl/miracl`（zh） | ✅ 可下载 | 备选（但语料是维基，不是业务场景） |
| `hfl/cmrc2018` | ✅ 已下载 | 单段落抽取，检索难度过低，只作跨语料验证 |

T2Ranking 的优势很具体：**原生中文真实搜索查询**（样例：「蜂巢取快递验证码摁错怎么办」）、
**4 级人工相关性标注**、**自带官方 BM25 与 DPR 基线 run**（后者正好能验证自己的实现）。

## 2. 子集构建（3.4GB 全量在 CPU 上不可行，所以要下采样）

全量 collection 3.41 GB / 300 万+ 段落。下采样必须**方法论上站得住**：

1. 选 **1000 条查询**（只选至少有 1 条正例的，否则召回恒为 0）；
2. 收进这 1000 条查询**全部被判定过**的段落 → 保证 qrels 在子集内**完整**；
3. 再从判定池随机补 **14000** 条干扰段落。

**产出**（`src/ingest/build_zh_t2ranking.py`，含 5 个单测）：

| 项 | 值 |
|---|---|
| 查询 | 1000（全部有正例） |
| 段落 | 30,365（16,365 判定 + 14,000 干扰） |
| qrels | 16,433 条（4 级：rel 0/1/2/3） |
| 下载耗时 | collection 3.41GB / 2.7 分钟（21 MB/s） |

> ⚠️ **必须带上的前提**：这是在 **pooled 判定池**上评测（标准 IR 做法），比在 300 万段落
> 全量里找要**容易**。引用指标时必须说明语料规模。

## 3. 中文分词：bigram（不需要 jieba）

原分词器 `simple_tokenize` 用 `[a-z0-9]+`，**中文基本全丢**：

```
simple_tokenize("蜂巢取快递验证码摁错怎么办") -> ['0'] 左右（只剩数字）
zh_tokenize(同一个 query) -> ['蜂巢','巢取','取快','快递',...] 共 15 个
```

`zh_tokenize` 用**字符二元组**（Lucene CJKAnalyzer 的经典做法），十行代码、零新依赖。

## 4. 检索结果（1000 条真实查询，对着真 qrels）

| 分词器 | nDCG@10 | Recall@100 | MRR@10 |
|---|---|---|---|
| **zh（bigram）** | **0.4749** | **0.8390** | **0.7116** |
| en_split（原缺陷实现） | 0.0498 | 0.0941 | 0.0763 |
| 差距 | **9.5 倍** | 8.9 倍 | 9.3 倍 |

**在真实人工标注上第三次确认了同一个结论：BM25 的弱是分词问题，不是算法问题。**
（第一次在英文语料 0.720→0.803；第二次在 CMRC2018 0.08→0.9967；这次在 T2Ranking 真 qrels 上 0.0498→0.4749。）

## 5. 与官方 BM25 基线的对照（验证实现是否正确）

官方 `dev.bm25.tsv` 是在**全量 300 万段落**上检索的结果。直接比会误导：

| 配置 | 语料 | nDCG@10 |
|---|---|---|
| 官方 BM25 基线 | 全量 300 万段落 | 0.2560 |
| 我的 BM25（bigram） | 30k 子集 | 0.4749 |

**我更高不是因为我更强，而是因为我的语料是被判定池富集过的（任务更容易）。**
这组对比本身就是「下采样让任务变简单」的量化证据。

**干净的对照**：把官方 run 过滤到「我的语料里也存在的文档」，让两边候选池一致：

| 配置（同候选池） | nDCG@10 |
|---|---|
| 官方 BM25 基线（过滤后） | **0.4638** |
| 我的 BM25（zh bigram） | **0.4749** |

差 **2.4%**，Top-10 重合率 **0.62**（970 题可比）。

**结论：我的分词与打分实现与官方基线在同一水平线上，实现是正确的。**
这正是当初那个 `split()` 分词 bug 缺失的对照物 —— 当时如果有官方基线可对，就不会得出
「BM25 不适配语料」的错误结论。

## 6. 还没做

1. **dense 对比**：bge-m3 在 30k 中文段落上向量化，CPU 约需 1.3 小时（30k × 0.153s）。要做才能给
   「中文上 dense vs BM25」的结论。
2. **混合检索 + 重排**：接 `HybridRerankRetriever`（中文需确认 bge-reranker 对中文的效果）。
3. **端到端（生成 + 判官）**：能复用 `answer_eval`，但 T2Ranking 是检索数据集、没有标准答案，
   需要换评估方式（只能测检索侧指标 + 忠实度，不能测答案正确率）。
4. **与英文轨道的定位区分**：英文轮次用代理指标（答案字符串）、中文轮次用真 qrels。**两套数字必须分开报。**
