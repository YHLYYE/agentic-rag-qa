# 中文语料可行性实验（CMRC2018）

> 起因：需要判断「是否值得加一份中文语料」，以及在中文上现有组件的表现。
> 结论：**值得做，而且实验顺带验证了一个悬而未决的猜测 —— BM25 的弱是分词问题，换语料后它确实能反超 dense。**
> 日期：2026-09-26 ｜ 全部为实测数据，无 LLM 调用（零成本）

---

## 1. 语料可用性实测（不是猜的）

| 数据集 | 状态 | 说明 |
|---|---|---|

样例：`《战国无双3》是由哪两个公司合作开发的？` → `光荣和ω-force`

---

## 2. 两个组件在中文上会直接失效（实测）

**① BM25 分词器**（`simple_tokenize` 用的是 `[a-z0-9]+`）：

```
query《战国无双3》是由哪两个公司合作开发的？
  simple_tokenize -> ['3']        ← 只剩数字！中文全被丢掉
```
→ 索引和查询都几乎无 token，BM25 打分全 0、排序等于随机。**这就是中文 HitRate 只有 0.08 的原因。**

**② 切块函数**（`chunk_text` 按 `text.split()` 切词）：

```
417 字符的中文段落 -> 按空格 split 只有 5 个 token -> 只切出 1 个 chunk（等于没切）
```
→ 中文长文档会退化成「一个 chunk 装完」，切块策略彻底失效。

**③ 字符 bigram 方案可行**（**不需要引 jieba**）：

```
bigram(query)   = ['战国','国无','无双','双3','3是','是由','由哪','哪两', ...] 共 16 个
bigram(context) = ['战国','国无','无双','双3','3是','是由','由光','光荣', ...] 共 361 个
```
这是 Lucene CJKAnalyzer 的经典做法，十行代码，无新依赖。

## 3. 检索效果实测（n=300，k=5，语料 848 段）

| 检索器 | HitRate@5 |
|---|---|
| dense（bge-m3） | **0.9900** |
| BM25（原分词器） | **0.0800** |
| **BM25（字符 bigram）** | **0.9967** |

### 三个结论

1. **`bge-m3` 的中文能力很强**（0.99）—— dense 这条路径不需要任何改动。
2. **BM25 在中文上从 0.08 → 0.9967，差 12 倍**，全部来自分词。这再次印证了英文语料上的那条教训：
   **BM25 的表现高度依赖分词质量，"BM25 弱"这类结论必须先排除实现缺陷。**
3. **BM25（bigram）反超了 dense**（0.9967 vs 0.9900）—— 正面回答了那个悬而未决的问题：
   「BM25 会不会只是不适配某个语料？」**会。换语料 + 正确分词后，它确实可以优于 dense。**

### 必须带上的 caveat（否则会过度解读）

- 这个任务**比英文那套简单得多**：848 个段落（vs 英文 10,682 chunks）、段落只有 417 字符、单段落抽取式（答案就在该段落里）。
- 两个检索器都**贴着天花板**（0.99+），区分度不足；0.9967 vs 0.9900 只差 **2 题/300**，**统计上不显著**。
- 所以只能说「在这个中文任务上两者持平、BM25 略优」，**不能**推广成「BM25 普遍优于 dense」。
- 单段落语料也意味着它**没有覆盖多段落多跳检索**，和当前英文语料的考察点不同。

## 4. 如果要正式加中文语料，需要改什么

| 改动 | 位置 | 工作量 |
|---|---|---|
| 中文分词（字符 bigram） | `src/rag/bm25.py` 加 `zh_tokenize` | ~10 行，无需新依赖 |
| 中文切块（按字符/标点，不按空格） | `src/ingest/chunk.py` | 中等 |
| 语料构建脚本 | 新增 `src/ingest/build_zh_index.py` | 中等 |
| 评估复用 | 现有 `retrieval_metrics` / `answer_eval` 可直接用（答案字符串匹配对中文同样成立） | 0 |
| dense 路径 | 无需改动（bge-m3 原生多语言） | 0 |

**成本提示**：真实端到端评估每题约 6~10 次 LLM 调用；中文索引在 CPU 上向量化 848 段约 **8 分钟**（本次实测 493.8s）。

---

## 5. 建议

**建议加，但作为「第二条轨道」，不要替换英文语料。** 理由：
1. 中文提问场景需要中文语料，而当前 demo 只接了英文语料；
2. 它是对前几轮结论的**跨语料验证**（尤其是「BM25 依赖分词质量」这条）；
3. 补上后项目可以正当地写「支持中英文检索」。

**但两个语料的数字必须分开报**：英文（HitRate@5 0.8700 / 答案正确率 0.9667）和中文（0.9900）不是一回事，
中文这套任务明显更简单，混在一起报会夸大效果。
